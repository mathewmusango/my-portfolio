# 开源与 Emuplane

!!! note "个人项目"
    Emuplane 是我个人的开源项目，独立于我的雇主开发。本页不描述任何雇主的系统。

AWS 模拟器能让一名开发者的笔记本用起来像 AWS，却不能让它可供多人使用：只有
一个隐含账户、一套落在本地磁盘上的凭证，通常连控制台都没有。Emuplane 就是我
为填补这个缺口而构建的控制平面。它挡在模拟器之前——在我的环境里是 MiniStack
——让账户、账户里的登录，以及为请求签名的客户端都成为真实且共享的东西。

## 为什么模拟器需要一个控制平面？

本地模拟器确实有用：不用 AWS 账户、不产生账单，就能把 S3、IAM 或 DynamoDB 放进
测试回路。可一旦不止一个人需要同一个模拟器，粗糙的边缘就露出来了：

- **只有一个账户，没有登录。** 所有人都是同一个调用者，所以一条本该拒绝某个用户
  的策略根本无法演练。
- **凭证躺在磁盘上。** 访问密钥被粘贴进 profile 和 shell：从不签发，也无从区分
  ——审计的起点只能是"某个人"。
- **没有控制台。** 模拟器就是一个 API，于是人想看的任何东西，都是一次 CLI 调用
  或一段手写脚本。
- **工具指向空处。** Terraform 和 AWS CLI 需要一个 endpoint，而每个工具都有自己
  被告知 endpoint 的方式。

Emuplane 正好回应这四个问题，也止步于此。**它不是 AWS 的替代品，项目本身就这么
说**——它让模拟器支持多用户、具备工具的形态；它不追求与 AWS 的功能对等。

## 架构

Emuplane 位于客户端与模拟器之间，并掌管模拟器所缺的标识层：

| 层 | 作用 |
|---|---|
| **Python API 网关** | 控制 API、访问密钥签发，以及客户端签名所指向的请求路径 |
| **React 控制台** | 浏览器界面，基于 AWS Cloudscape 设计系统构建 |
| **DynamoDB** | 账户、身份与会话状态——通过模拟器本身存储 |
| **Docker Compose** | 一条命令同时拉起控制平面与模拟器 |
| **GitHub Actions** | 14 个 workflow，覆盖测试、扫描、镜像与发布 |

Terraform 和 AWS CLI 把 endpoint 指向 Emuplane。Emuplane 保存账户及其中的登录，
签发这些客户端用来签名的访问密钥，并在同一份状态之上提供控制台与控制 API ——
所以浏览器里看到的，就是 CLI 正在操作的东西。

### Python API 网关

网关是唯一必须在身份方面被信任的组件。它保存账户及其中的登录，签发客户端用来
签名的访问密钥——所有与模拟器对话的工具，共用一个 endpoint、一套身份模型。

### React 控制台

控制台基于 **AWS Cloudscape** —— AWS 自家的开源设计系统 —— 构建，因此模拟器的
控制台读起来就像人们已经熟悉的控制台。它是控制 API 之上的前端，这让行为只留在
一处：浏览器里的一条路由和一次 CLI 调用是同一个操作。

### 数据与本地运行时

状态存放在**经由模拟器访问的 DynamoDB** 中，这让技术栈保持诚实：Emuplane 不会
要求一个模拟器无法提供的数据库。**Docker Compose** 把控制平面和模拟器一起拉起，
因此一台新机器或一个 CI job 用一条命令就能得到可用的模拟器。

## 交付内容

从 **2026-11-05 到 2026-11-23**，这个项目从零走到可用产品：**三周内 16 个 git
tag，从 `v0.1.0` 到 `v0.9.0`**，**15 个 GitHub release**，**337 次提交**，约
**22,800 行 Python** 外加一个 React 前端，以及 **14 个 CI workflow**。

### 控制台功能面

- **S3** —— bucket、对象、版本、ACL、生命周期 / 通知 / 日志文档，以及分片上传。
- **IAM** —— 用户、组、角色、策略、身份提供方、账户设置、凭证报告与 API 浏览器。
- **账户与登录** —— 一套账户模型，登录发生在账户之内，而不是一个隐含身份。
- **按服务划分的覆盖台账** —— 每个服务自己说明哪些已实现、哪些没有。

### IAM、MFA 与登录

IAM 是模拟器最容易造假、也最难做对的地方，所以投入也最多：控制台认证路径中的
**TOTP MFA** 与显式的**登录挑战**，以及**宣称支持的 98 项 IAM 操作全部测试**
（98/98）。

### 发布流水线

这个仓库刻意按真实开源项目的规矩运转：

- **`main` 只能通过 PR** —— 只允许 squash，一个 PR 对应一个 issue，正文写
  `Closes #N`。
- **标签决定发布** —— issue 的标签决定变更落到 changelog 的哪一节，以及版本号的
  哪一位递增。
- **文档按发布冻结** —— 一个发布的文档随该发布一起冻结。

### 供应链

- **Trivy 把关每一次发布** —— 扫描是发布条件，不是一份报告。
- **GHCR 上的容器镜像**，标签为 `X.Y.Z` 与 `latest`。
- **每次发布都附带 SBOM（SPDX）、`SHA256SUMS` 与 `IMAGE-DIGEST`**，因此不必信任
  构建它的流水线也能校验产物。
- **前端 400 多个 pytest 测试与 121 个 vitest 测试**。
- **OpenSSF Best Practices 徽章 100%。**

## 经验教训

- **模拟器的缺口该写在一份公开的边界页里。** 用户不断撞上"这个模拟器不模拟这个"
  与"Emuplane 没实现这个"之间的边界；一份写明边界的页面能把争论变成一次指向。
- **按服务划分的覆盖台账比功能列表更有价值。** 说清哪些覆盖了、哪些是刻意不覆盖
  的，才让一个模拟器在测试中值得信赖——也让"98/98 项 IAM 操作"这样的说法可以被
  核对。
- **控制台的路由需要服务端入口。** 单页应用里的客户端路由，在有人直接输入或刷新时
  是到不了的；控制台的每条路由都必须作为真实的入口存在。
- **难的从来不是模拟器，而是身份模型。** 一旦账户和密钥是真的，其他一切都有了
  落脚之处。
